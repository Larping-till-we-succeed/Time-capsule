# Android / Rust API contract (proposed)

Status: **proposed, not implemented.** The Rust engine in `src/` exposes no stable FFI
surface. Nothing in this document describes existing functionality. It records the contract
the Android side needs so the Rust contributor can review, adjust or reject it before UniFFI
bindings are generated.

## Kotlin-facing interface

`dev.timecapsule.app.core.rust.TimeCapsuleCore`:

```kotlin
interface TimeCapsuleCore {
    suspend fun listProjects(): List<Project>
    suspend fun createProject(name: String, directoryUri: String): Project
    suspend fun listSnapshots(projectId: ProjectId): List<Snapshot>
    suspend fun createSnapshot(projectId: ProjectId, title: String, note: String): Snapshot
    suspend fun compareSnapshots(projectId: ProjectId, firstSnapshotId: SnapshotId, secondSnapshotId: SnapshotId): SnapshotDiff
    suspend fun restoreSnapshot(projectId: ProjectId, snapshotId: SnapshotId)
    suspend fun getProjectStatistics(projectId: ProjectId): ProjectStatistics
}
```

`TimeCapsuleRepository` (the interface the UI depends on) extends `ProjectRepository` and
`SnapshotRepository` and adds a `dataSource: DataSource` property. A UniFFI-backed
implementation implements both `TimeCapsuleRepository` and `TimeCapsuleCore`.

## Proposed data carried across the boundary

| Kotlin type | Rust-side expectation | Notes |
| --- | --- | --- |
| `ProjectId`, `SnapshotId` | opaque string IDs | Android treats them as opaque. Rust owns generation and validation. |
| `Project` | struct | `directory` is a `content://` tree URI string on Android, not a path. |
| `Snapshot` | struct | timestamps as epoch millis (or RFC3339). Android converts to `Instant`. |
| `Branch` | struct | `isActive` derived from the project's active branch. |
| `SnapshotDiff` | struct + list of `FileChange` | textual diff is a separate, optional payload. |
| `FileChange.kind` | enum `Added` / `Modified` / `Deleted` | line counts are engine-derived. |
| `TextualDiff` | enum `NotAvailable` / `Available(unified)` | Android never fabricates patch text. |
| `ProjectStatistics` | struct | activity is a list of `(date, count)` buckets. |
| `DailyActivity.date` | epoch day or ISO date | Android renders it as a `LocalDate`. |

## Error model

- Rust errors should map to a small sealed error type on the Kotlin side
  (`ProjectNotFound`, `SnapshotNotFound`, `InvalidComparison`, `StorageAccess`, `Engine`).
- Android converts them to user-facing messages through `Throwable.displayMessage()`.
- Cancellation must propagate as cancellation, not as a generic error.

## Storage bridge (`ProjectStorageGateway`)

The Rust core cannot open Android `content://` URIs. The Android adapter is responsible for:

- resolving a granted tree URI into readable content through `ContentResolver`;
- streaming file bytes (or file descriptors) to the core;
- reporting progress and cancellation for long operations.

`SafProjectStorageGateway` already enumerates granted trees and reports entry counts. The
byte-streaming half is intentionally unimplemented and is the main open item.

## Unresolved decisions requiring coordination

1. **Snapshot identity and ordering.** Should IDs be generated by Rust (likely) and should
   Android ever sort by anything other than `createdAt`? The fake repository sorts by
   `createdAt` descending.
2. **Branch model.** Is a branch a first-class entity with its own metadata, or just a string
   tag on a snapshot? The Android model assumes the latter for now.
3. **Directory binding.** `createProject(name, directoryUri)` assumes the core accepts a
   `content://` URI and stores it. Alternatively the core could accept an opaque storage
   handle provided by Android. This needs agreement.
4. **Restore semantics.** `restoreSnapshot` mutates the working directory. On Android that
   means writing through SAF, which requires per-file write permission and conflict handling.
   The core's restore contract (atomic vs. incremental, rollback) is undefined.
5. **Statistics scope.** Should `getProjectStatistics` include activity for all time or a
   rolling window? Android currently requests 14 daily buckets; the window length may need to
   be a parameter.
6. **Threading and progress.** UniFFI calls are blocking; Android wraps them in coroutines.
   Long operations (create snapshot, restore) need a progress/cancellation contract.
7. **Offline and partial state.** How should Android represent a project whose directory
   grant was revoked but whose snapshot history still exists?
8. **Versioning.** A `coreVersion()` (or similar) is needed so Android can gate features by
   engine capability. Not in the proposed interface yet.

## What is deliberately NOT in this contract

- Snapshot creation triggers (manual, automatic, on-save) — these are app-level policy.
- UI-specific filters, search or pagination.
- Any filesystem path: Android does not have one.
